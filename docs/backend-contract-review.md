# Q1. 속도 검증 임계값 — 위치 스푸핑 방어

## 결론

제안한 속도 검사(150 / 300km/h) 방향은 맞음. 두 가지만 바꾸자.

1. 판정 조건을 **시간이 아니라 거리 기준**으로 — 오탐 막으려던 조건이 그대로 공격 통로가 됨
2. **App Check을 방어 1단으로 추가** — 속도 검사만으로는 가장 흔한 스푸핑을 못 막음. 앱 쪽 작업 필요

---

## 1. 속도 검사 — 조건을 거리 기준으로

### 문제

GPS는 사용자가 가만히 있어도 측정값이 30~50m씩 흔들린다. 짧은 간격의 두 측정값으로 속도를 계산하면 이 흔들림이 시속 100km 이상으로 잡힌다. 정상 사용자가 스푸퍼로 판정돼 티켓을 못 받는다.

이걸 막으려고 "측정 간격이 30초 미만이면 속도 계산을 생략" 하는 규칙을 먼저 검토했는데, 그러면 28초마다 좌표를 옮기는 방식으로 검사를 영구히 회피할 수 있다. 시간 조건 자체가 구멍이다.

### 해결

막아야 할 대상은 "짧은 시간"이 아니라 "작은 거리 흔들림"이었다. 조건을 바꾼다.

> **두 측정값 사이 거리가 200m 미만이면 속도 계산을 생략한다. 200m 이상이면 간격과 무관하게 항상 계산한다.**

- GPS 흔들림은 200m를 넘지 않는다 → 정상 사용자 오탐이 사라진다
- 실제 순간이동은 거리가 크므로 2초 만에 옮겨도 항상 걸린다
- 시간 조건이 없으니 회피 통로도 없다

### 확정값

| 항목 | 값 |
| --- | --- |
| 세션 내 연속 측정 | 200m 이상 이동한 쌍만 계산, **150km/h** 초과 시 거부 |
| 직전 발행 티켓 대비 | **300km/h** 초과 시 거부 (KTX·국내선 커버) |
| 거리 계산 | GPS 오차 반경만큼 차감 후 계산 |

거부는 계약서대로 `verified: false`, `reason: 'implausible_speed'`. throw 아님.

---

## 2. App Check 추가 — 앱 쪽 작업이 필요한 부분

### 왜 속도 검사만으로는 부족한가

Fake GPS 류 앱으로 좌표를 목적지에 고정해두고 가만히 있으면 속도가 0이라 속도 검사에 걸리지 않는다. 반경 검사도 통과한다. **현재 계약서의 검사만으로는 가장 흔한 스푸핑 수법을 못 막는다.**

### 방어 3단 구성

| 단계 | 무엇 | 막는 것 |
| --- | --- | --- |
| 1 | **Firebase App Check** (Play Integrity / App Attest) | 뜯어고친 APK, 에뮬레이터, 루팅·탈옥 기기, 앱 없이 함수 직접 호출 |
| 2 | **OS의 mock location 플래그** | 개발자옵션으로 도는 Fake GPS 앱 (루팅 불필요, 가장 흔함) |
| 3 | **반경 + 속도 검사** (현재 계약서) | 위 둘을 뚫고 들어온 케이스 |

셋이 서로 다른 구멍을 막는다. 1단이 없으면 앱을 고쳐 2·3단을 무력화할 수 있어서 App Check이 사실상 전제 조건이다. Firebase 기능이라 백엔드 쪽은 켜기만 하면 된다.

### 앱 쪽에 필요한 작업

1. `@react-native-firebase/app-check` 설치 및 초기화
2. Firebase 콘솔 등록(Play Integrity / App Attest)은 백엔드에서 처리
3. `verifyLocation` 요청에 `isMock: boolean` 추가
   - Android: `Location.isFromMockProvider()` (API 31+ 는 `isMock`)
   - iOS: 해당 API 없음. `false` 고정으로 보내고 App Check이 커버

### 계약서 변경 요청

```ts
// verifyLocation request
{
  placeId: string;
  lat: number;
  lng: number;
  accuracy: number;
  capturedAt: string;
  sessionId?: string;
  isMock: boolean;      // ← 추가. 기기가 보고한 mock location 여부
}

// reason union
'out_of_radius' | 'implausible_speed' | 'poor_accuracy' | 'mock_location'  // ← 추가
```

`isMock: true` 면 `verified: false` + `reason: 'mock_location'`. 인증 실패 화면에서 어떻게 표시할지는 앱 쪽 판단에 맡긴다.

---

## 3. 한계

100% 차단은 불가능하다. 업계 표준도 완전 차단이 아니라 **뚫는 비용을 보상보다 비싸게 만드는 것**이 목표다. 티켓 보상이 응모권 수준이면 위 3단으로 충분하다고 본다.

---

## 필요한 답변

1. `isMock` 필드와 `'mock_location'` 사유 추가 — 괜찮은지
2. App Check 앱 쪽 연동 — 일정상 언제 가능한지 (백엔드는 Phase 4 함수 배포 때 켜면 됨)
3. 속도 임계값 150 / 300km/h — 이견 있는지

# Q2. 한 장소 재발행 쿨다운

## 결론

재발행 가능 + 쿨다운, 제안대로 간다. 값은 **30일**.

한 번의 여행에서 두 번 이상 인증되는 상황을 막는 것이 기준이다. 하루 단위로 잡으면 같은 여행 중 재발행이 열리고, 장소당 1회로 잠그면 재방문 이유가 사라진다. 30일이면 "한 번 다녀온 곳은 다음 시즌에 다시" 라는 주기가 된다.

## 확정값

| 항목 | 값 |
| --- | --- |
| 쿨다운 | 같은 사용자 · 같은 장소 기준 **30일** |
| 검사 위치 | **`issueTicket` 한 곳에서만** |
| 판정 기준 | 해당 사용자의 그 장소 마지막 `tickets.issuedAt` |

`verifyLocation` 에는 쿨다운 검사를 넣지 않는다. 같은 검사를 두 함수에 중복으로 두면 규칙이 갈라질 때 원인을 찾기 어렵다. 발행 권한은 `issueTicket` 하나가 갖는다.

## 계약서 변경 요청

`issueTicket` 에러 목록에 추가:

```ts
failed-precondition
  details.errorCode: 'cooldown_active'
  details.nextAvailableAt: string   // ISO 8601. "n일 뒤 가능" 표시용
```

기존 `grant_expired` / `grant_consumed` 와 같은 형태다.

## 앱 쪽 요청 — 사전 표시

쿨다운이 30일이라 헛걸음 비용이 크다. 2주 전에 다녀온 곳을 다시 방문 → GPS 인증 통과 → 사진 촬영 → 마지막에 거부, 라는 흐름이 실제로 발생한다.

이건 백엔드 작업 없이 앱에서 해결된다. `tickets` 는 **본인 문서 읽기가 규칙상 허용**되므로, 장소/상세 화면에서 자기 티켓만 조회해 다음 발행 가능일을 미리 띄우면 된다.

- 서버는 그대로 `issueTicket` 한 곳에서만 강제 (검사 중복 없음)
- 앱의 표시는 안내일 뿐이고 판정 권한이 아니므로 trust boundary 위반이 아니다

카메라 진입을 앱에서 막을지, 안내만 띄울지는 앱 쪽 판단에 맡긴다.

## 필요한 답변

1. `'cooldown_active'` 에러 코드와 `nextAvailableAt` 추가 — 괜찮은지
2. 장소/상세에 다음 발행 가능일 표시 — 넣을 수 있는지

# Q3. `serial` 생성 방식

## 결론

전용 포맷으로 간다. 접두사는 `PD-`.

```
PD-7K2M-9QX4-B3TZ
```

## 사양

| 항목 | 값 |
| --- | --- |
| 형식 | `PD-XXXX-XXXX-XXXX` (고정 길이 19자) |
| 문자 집합 | Crockford Base32 — 대문자 + 숫자, `I` `L` `O` `U` 제외 |
| 엔트로피 | 랜덤 8바이트 (64비트) |
| 생성 위치 | `issueTicket` 내부, 서버에서만 |
| 중복 검사 | 하지 않음 |

문자 집합에서 `I` `L` `O` `U` 를 뺀 이유는 `1`/`I`, `0`/`O` 혼동 때문이다. 사용자가 티켓 번호를 눈으로 읽거나 불러줄 수 있는 형태로 둔다.

중복 검사를 생략하는 이유: 64비트 랜덤이면 티켓 1억 장을 발행해도 충돌 확률이 무시 가능한 수준이다. 검사를 넣으면 발행마다 조회가 한 번 늘고, 트랜잭션도 복잡해진다. 값어치가 없다.

## 문서 ID를 쓰지 않은 이유

Firestore 자동 ID(`x7Kd9Lm2QpRw3Nv8ZaB1`)를 그대로 쓰면 코드가 0줄이지만, 티켓 발행 화면은 실물 티켓처럼 바코드까지 달아 디자인돼 있다. 거기 찍히는 번호가 데이터베이스 내부값으로 보이면 제품 인상이 깎인다. 티켓 자체가 이 앱의 수집 대상이라 번호도 제품의 일부로 본다.

## 앱 쪽 확인 사항

바코드 심볼로지가 정해져 있는지 알려달라. Code128이면 위 문자 집합이 그대로 들어간다. 혹시 숫자 전용 심볼로지(EAN·UPC 등)를 쓰고 있으면 알려주면 숫자만으로 다시 잡겠다.

## 필요한 답변

1. 바코드 심볼로지 — Code128인지, 숫자 전용인지

# Q4. EXIF 제거

## 결론

제거한다. 다만 **담당을 백엔드가 아니라 앱으로 옮기는 것을 요청한다.** 대상은 티켓 사진과 커뮤니티 게시글 사진 둘 다.

## 왜 백엔드가 할 수 없나

계약서상 사진은 앱이 Storage에 직접 업로드하고, `issueTicket` 은 업로드가 끝난 뒤 경로 문자열만 받는다. 서버 손에 파일이 들어오는 시점 자체가 없다.

```
앱 ──사진──▶ Storage        ← EXIF가 이미 저장된 상태
앱 ──경로──▶ issueTicket    ← 서버는 여기서 처음 개입
```

사후에 지우려면 Storage 트리거 함수를 하나 더 만들어 파일을 다시 읽고 다시 써야 한다. 함수가 늘고, 재작성이 끝나기 전에 `issueTicket` 이 원본을 참조하는 타이밍 문제도 생긴다. 비용 대비 손해다.

## 앱에서는 사실상 공짜

앱은 이미 편집 화면에서 사진을 다룬다. **이미지를 다시 인코딩하면 EXIF는 그 과정에서 사라진다.** `expo-image-manipulator` 로 리사이즈나 압축을 한 번 거치면 끝이고, 별도 라이브러리가 필요 없다.

## 클라이언트에 맡겨도 되는 이유

GPS 판정은 클라이언트를 신뢰하면 안 된다. 티켓이라는 보상이 걸려 있어 공격 동기가 있기 때문이다.

EXIF는 성격이 다르다. **사용자 본인의 사진에 담긴 본인의 프라이버시**이고, 앱을 고쳐 자기 EXIF를 남겨도 손해 보는 건 본인뿐이다. 공격 동기가 없으므로 trust boundary 대상이 아니다.

좌표는 서버가 `verificationSessions` 에 이미 기록하고 있어, EXIF를 지워도 잃는 데이터는 없다.

## 계약서 변경 요청

Open questions 4번 항목의 담당을 **앱**으로 표기.

Cloud Storage 절의 규칙에는 백엔드가 별도로 넣을 것이 없다. 사이즈 캡과 `contentType` 검사는 기존대로 규칙에서 강제한다.

## 필요한 답변

1. 티켓 사진과 커뮤니티 사진 업로드 경로 양쪽 모두에 재인코딩이 들어가는지

# Q5. GPS 정확도 게이트

## 결론

거부 기준을 둔다. **전역 고정 65m.**

```ts
accuracy > 65  →  verified: false, reason: 'poor_accuracy'
```

`reason: 'poor_accuracy'` 는 계약서에 이미 정의돼 있어 응답 스키마 변경이 없다. **필드 추가도 없다.**

## 왜 게이트가 필요한가

기기가 보고하는 `accuracy` 는 오차 반경이다. `accuracy: 200` 이면 사용자는 보고된 지점에서 반경 200m 안 어딘가에 있다는 뜻이고, 이 상태에서는 "50m 이내" 판정이 의미를 갖지 못한다. 게이트가 없으면 근처만 배회해도 티켓이 나온다.

## 왜 65m인가

| 기준값 | 결과 |
| --- | --- |
| 50m (반경과 동일) | 논리적으로는 깔끔하지만 안드로이드 도심에서 정상 사용자가 계속 튕긴다. 실측 40~60m가 흔하다 |
| **65m** | 도심 오탐을 대부분 흡수. 최악의 경우 115m 밖 사용자가 통과 |
| 100m | 거의 안 튕기지만 50m 검사가 사실상 무의미해진다 |

## 장소별 필드를 두지 않는 이유

`radiusMeters` 처럼 `places` 에 `maxAccuracyMeters` 를 두는 안을 검토했으나 채택하지 않았다. **장소가 늘어날수록 사람이 손으로 관리할 수 없는 값**이 되고, 실제로는 대부분 기본값으로 남는다. 관리 비용만 늘고 쓰이지 않는 필드가 된다.

전역 상수 하나로 두고, 특정 장소에서 반복적으로 문제가 확인되면 그때 장소별로 쪼갠다. 스키마 변경 없이 시작할 수 있는 쪽을 택했다.

## 부수 규칙 — 거부된 측정은 세션에 기록하지 않음

Q1의 속도 검사는 `verificationSessions.readings` 에 쌓인 측정값들로 계산된다. 오차 200m짜리 측정이 이 배열에 섞이면 속도 계산이 오염되어 정상 사용자가 스푸퍼로 판정될 수 있다.

정확도 미달로 거부한 측정은 `readings` 에 넣지 않는다.

## 앱 쪽 안내

`poor_accuracy` 는 사용자가 조치할 수 있는 실패다. 인증 실패 화면에서 "하늘이 트인 곳으로 이동 후 재시도" 류의 안내를 넣어주면 재시도 성공률이 올라간다. 현재 화면은 거리·반경·정확도를 표로 보여주므로 자리는 이미 있다.

## 필요한 답변

없음. 백엔드 단독으로 확정 가능하며 스키마 변경도 없다. 인증 실패 화면 문구만 참고.

# 스키마 지적

계약서의 Open questions 외에, 문서를 구현 관점에서 읽으며 발견한 항목이다. A·D·F는 현재 스키마 그대로는 함수를 작성할 수 없는 건이고, 나머지는 비용·표기·단순화 건이다.

## A. grant 토큰을 저장할 곳이 없음

### 문제

`verifyLocation` 은 성공 시 `grant: { token, expiresAt }` 을 반환하고, `issueTicket` 은 "grant가 미만료·미사용이며 호출자 소유인지" 검증해야 한다.

그런데 `verificationSessions` 에는 `grantExpiresAt?` 만 있다. **토큰 값 자체도, 사용 여부도 저장되는 곳이 없다.** 지금 스키마로는 `issueTicket` 의 검증 세 가지 중 두 가지를 구현할 수 없다.

### 해결 — 새 필드를 만들지 않는다

`grant.token` 의 값을 **`sessionId` 로 정의한다.**

- **소유자 확인**: 세션 문서의 `userId` 가 호출자와 같은지 본다. 이미 있는 필드다
- **만료 확인**: `grantExpiresAt` 을 본다. 이미 있는 필드다
- **사용 여부**: `status` 를 `'consumed'` 로 바꾼다. union에 값 하나만 추가

세션 ID를 추측 불가능한 난수로 따로 만들 필요가 없다. 남의 세션 ID를 알아내도 `userId` 검사에서 막히고, `verificationSessions` 는 클라이언트가 쓸 수 없으므로 위조도 불가능하다. 별도 토큰은 방어력을 더하지 않는다.

### 변경

```ts
// verificationSessions.status
'active' | 'verified' | 'consumed' | 'expired'   // 'consumed' 추가
```

`issueTicket` 요청의 `grantToken: string` 은 이름 그대로 둔다. **앱 코드 변경 없음** — 응답으로 받은 `grant.token` 을 그대로 넘기면 된다.

> 건너뜀: 별도 난수 토큰과 해시 저장. `userId` 검사가 이미 같은 일을 함.

---

## B. `readings` 배열이 무한히 증가함

### 문제

`verificationSessions.readings` 는 인증 시도마다 원소가 늘어난다. Firestore는 배열 원소 하나를 추가할 때도 **문서 전체를 다시 쓴다.** 사용자가 반경 밖에서 계속 재시도하면 문서가 계속 커지고 쓰기 비용도 같이 커진다. 문서 1MB 한도도 있다.

### 해결

**최근 5개만 유지한다.** 6번째부터는 가장 오래된 것을 밀어낸다.

Q1에서 확정한 속도 검사는 직전 측정값 하나만 있으면 계산된다. 5개를 남기는 것은 실패 원인을 볼 여유분이고, 그 이상은 쓰이지 않는다.

문서 크기가 상수로 고정되고, 새 필드도 에러 코드도 늘지 않는다.

> 건너뜀: 리딩 개수 상한 도달 시의 별도 거부 코드. 오래된 것을 버리면 상한 자체가 없어짐.

## C. 만료된 세션이 영구히 남음

### 문제

인증에 실패한 세션, 티켓 발행까지 안 간 세션이 지워지지 않는다. 사용자 한 명이 하루에 여러 개를 만들고, 아무도 읽지 않는 문서가 계속 쌓인다.

### 해결 — Firestore TTL 사용

정리용 스케줄 함수를 만들지 않는다. Firestore에 **TTL 정책**이 내장돼 있다. 필드 하나를 지정해두면 그 시각이 지난 문서를 Firestore가 알아서 지운다.

```ts
// verificationSessions
expiresAt: Timestamp   // 추가. startedAt + 24시간
```

콘솔에서 `verificationSessions.expiresAt` 에 TTL 정책을 켜면 끝. **코드 0줄, 함수 0개.**

`grantExpiresAt` 을 재사용할 수 없는 이유는 그것이 선택 필드이고(인증 성공 시에만 존재) 값도 짧기 때문이다. 실패한 세션에는 아예 없어서 영원히 안 지워진다.

> 건너뜀: 정리용 스케줄 함수. 플랫폼 기능이 같은 일을 무료로 함.

## D. `users` 문서를 만드는 주체가 없음

### 문제

`users/{uid}` 는 "회원가입 시 생성"이라고 적혀 있는데, 카운터 3개(`ticketBalance`·`ticketsIssued`·`placesVisited`)가 **function-only** 다. 그런데 계약서의 함수는 세 개뿐이고 그중 어느 것도 사용자 문서를 만들지 않는다. 회원가입 직후 사용자 문서가 존재하지 않는다.

### 해결 — 함수를 추가하지 않는다

**클라이언트가 자기 문서를 만들고, 규칙이 카운터를 0으로 강제한다.**

```
users 생성 규칙:
  - 문서 ID == 호출자 uid
  - ticketBalance == 0, ticketsIssued == 0, placesVisited == 0
  - 이 조건을 어기면 생성 거부

users 수정 규칙:
  - nickname, avatarUrl 만 변경 가능 (기존 표 그대로)
```

카운터 조작은 규칙이 막고, 문서 생성은 앱이 회원가입 폼에서 이미 하는 일에 한 번 더 얹으면 된다. Auth 트리거 함수를 추가하면 함수가 4개가 되고 배포 단위가 하나 늘어난다.

문서 생성 없이 인증만 하고 이탈하는 경우도 문제가 되지 않는다. `issueTicket` 은 `merge` 옵션으로 증가시키므로 문서가 없으면 그 시점에 생성된다.

### 계약서 변경

Write ownership 표의 `users` 행 클라이언트 write를 다음으로 수정:

> 자기 문서 생성(카운터는 0 고정) · 자기 `nickname`, `avatarUrl` 수정. 카운터는 절대 불가

> 건너뜀: Auth onCreate 트리거 함수. 규칙 3줄이 같은 보장을 함.

## E. `tickets` 읽기 — 규칙은 필터가 아님

### 문제

Write ownership 표에 `tickets` 클라이언트 read가 "본인 것 + 남의 것 중 `visibility == 'public'`" 으로 적혀 있다.

이 표현이 Firestore에서 흔히 오해를 부른다. **보안 규칙은 결과를 걸러주지 않는다.** 규칙은 쿼리 자체가 안전한지만 판정한다. 앱이 `where('visibility', '==', 'public')` 없이 티켓 목록을 조회하면, 공개 티켓만 돌아오는 게 아니라 **쿼리 전체가 `permission-denied` 로 거부된다.**

스키마 문제는 아니지만 앱이 이걸 모르면 원인 찾는 데 시간이 든다.

### 해결

스키마 변경 없음. 규칙은 조회 종류별로 나눠 쓴다.

- 문서 하나 직접 읽기: 본인 것이거나 `visibility == 'public'` 이면 허용
- 목록 조회: `userId == 본인` 또는 `visibility == 'public'` 조건이 **쿼리에 포함돼 있어야** 허용

### 앱 쪽 요청

티켓 목록 쿼리에는 위 두 조건 중 하나가 항상 들어가야 한다. 계약서에 한 줄 명시해두면 나중에 원인 추적이 빨라진다.

## F. `idempotencyKey` 를 저장할 곳이 없음

### 문제

`enterRaffle` 요청에 `idempotencyKey` 가 있는데, 이 값이 **어디에도 저장되지 않는다.** `raffleEntries` 스키마에 없다. 저장하지 않으면 같은 키로 다시 호출해도 서버가 알아볼 방법이 없고, 네트워크 재시도 한 번에 티켓이 두 번 차감된다.

### 해결 — 필드를 만들지 않는다

**응모 문서의 ID를 키로 만든다.**

```
raffleEntries 문서 ID = {uid}_{raffleId}_{idempotencyKey}
```

트랜잭션 안에서 이 ID의 문서가 이미 있으면 차감하지 않고 기존 `entryId` 를 그대로 반환한다. 없으면 새로 만든다. 같은 키로 몇 번을 호출해도 결과가 하나로 수렴한다.

Firestore 문서 ID는 같은 컬렉션 안에서 유일성이 보장되므로, 별도 조회나 중복 검사 컬렉션이 필요 없다.

### 형식 제약

문서 ID에 `/` 가 들어갈 수 없어 키 형식을 제한한다.

```
idempotencyKey: 영문·숫자·`-`·`_` 만, 1~64자
어기면 invalid-argument
```

앱은 UUID를 그대로 쓰면 조건을 만족한다. 응모 화면 진입 시 한 번 생성해서 재시도할 때 같은 값을 보내면 된다.

> 건너뜀: 별도 idempotency 기록 컬렉션과 TTL. 문서 ID가 같은 일을 함.

## G. `places.ticketCount` 표기 누락

### 문제

`places.ticketCount` 는 "여기서 발행된 티켓 수"인데 **function-only 표기가 없다.** 표기가 없으면 규칙 작성 시 클라이언트 쓰기를 열어둘 여지가 생기고, 그러면 홈 추천 순위를 사용자가 조작할 수 있다.

### 해결

표기만 추가한다.

```
ticketCount | number | **Function-only.** issueTicket 이 증가시킴
```

### 함께 정리 — `placesVisited` 증가 조건

`users.placesVisited` 는 "처음 방문한 장소"에서만 늘어야 하는데 조건이 계약서에 없다. Q2의 쿨다운 검사가 이미 "이 사용자의 이 장소 마지막 티켓"을 조회하므로, **그 결과가 비어 있으면 첫 방문**이다. 쿼리 하나로 둘 다 해결된다.

`issueTicket` 이 한 트랜잭션에서 증가시키는 값 정리:

| 대상 | 조건 |
| --- | --- |
| `users.ticketBalance` | 항상 +1 |
| `users.ticketsIssued` | 항상 +1 |
| `users.placesVisited` | 해당 장소 첫 발행일 때만 +1 |
| `places.ticketCount` | 항상 +1 |

## H. `geohash` 제거 제안

### 문제

`places.geohash` 가 "지도 근접 쿼리에 필요"로 되어 있는데, 정밀도도 쿼리 방식도 정해져 있지 않다.

정하려면 따라오는 것이 많다. geohash 범위 쿼리는 셀 경계 때문에 한 번에 끝나지 않고 보통 4~9개의 범위 쿼리로 쪼개진다. 결과를 합치고 중복을 제거한 뒤 실제 거리로 다시 걸러야 하며, 복합 인덱스와 `geofire-common` 의존성이 따라온다.

### 근접 쿼리 자체가 요구사항과 맞지 않는다

지도는 **전국이 한 화면에 보이는 수준에서 시작해 확대해 들어가는** 방식이다. 축소 상태에서 가까이 있는 핀들은 묶어서 표시하되, **거리가 멀다는 이유로 핀이 사라지면 안 된다.**

즉 지도는 어느 시점에도 전체 촬영지를 알고 있어야 한다. `geohash` 는 "내 주변 것만 골라오기" 를 위한 장치이므로, 전부 필요한 화면에서는 쓸 자리가 없다.

### 거리 계산도 앱에 필요 없다

지도는 좌표를 핀으로 찍기만 하면 된다. 거리가 실제로 쓰이는 곳은 **인증 시점 한 번뿐이고, 그 계산은 `verifyLocation` 이 서버에서 한다.**

앱이 거리를 미리 계산하거나 저장할 이유가 없다. 화면에 표시되는 거리는 계약서대로 인증 응답의 `distanceMeters` 를 그대로 쓰면 된다.

### 해결

```
places.geohash 삭제
지도: places 전체 조회 → 좌표 그대로 핀 렌더링
```

- 복합 인덱스 불필요
- 지오 라이브러리 불필요
- 클러스터링은 화면 렌더링 영역이라 백엔드와 무관

촬영지는 운영자가 시드하는 데이터라 사용자 생성 데이터처럼 급증하지 않는다. 앱에 MMKV 캐시가 이미 있어 지도를 열 때마다 다시 읽지도 않는다.

### 한계와 되돌리는 지점

촬영지가 **1,000개를 넘으면** 전체 조회의 응답 크기가 부담이 된다. 다만 그때도 해법은 geohash가 아니다. 전국 표시라는 요구는 그대로이므로, 지도용으로 좌표와 이름만 담은 경량 목록을 따로 두거나 `updatedAt` 기준 증분 갱신으로 전환하는 쪽이 맞다.

> 건너뜀: geohash 인덱스·범위 쿼리·지오 라이브러리. 전국 표시 요구가 있는 한 도입 시점 없음.

# 합의 제안 — 규칙 작성 전 확정이 필요한 2건

보안 규칙(Phase 3)은 필드 이름과 쓰기 주체를 코드에 직접 박는다. 위 항목 대부분은 규칙과
무관하지만, **D와 E 두 건은 규칙의 모양 자체를 바꾼다.** 먼저 쓰면 회신 후 절반을 버리게
되므로 아래 안으로 확정하고 진행하려 한다.

**이의가 없으면 이대로 작성한다.** 반대나 수정 의견이 있으면 알려주면 그에 맞춰 쓴다.
나머지 항목은 회신을 기다리지 않고 지금 작성한다.

## 1. `users` 문서는 클라이언트가 만든다 (D)

```
allow create: if request.auth.uid == uid
              && request.resource.data.ticketBalance == 0
              && request.resource.data.ticketsIssued == 0
              && request.resource.data.placesVisited == 0;

allow update: if request.auth.uid == uid
              && 변경 필드가 nickname, avatarUrl, bio, followedArtistIds,
                 profileVisibility, locale 여섯 개 안에 있을 것;
```

회원가입 직후 앱이 `users/{uid}` 를 만들고, 규칙이 카운터 3개를 0으로 강제한다.

> **2026-08-22 정정.** 최초 초안의 `allow update` 는 `nickname` 과 `avatarUrl` 두 개만
> 허용했다. 계약서 write-ownership 표는 여섯 필드를 허용하며, 두 개로 쓰면 프로필 편집·언어·
> 최애 찾기가 `permission-denied` 로 실패한다. 앱 쪽 지적을 받아 위와 같이 정정했고
> Phase 3 규칙은 이 여섯 필드로 작성됐다. `allow create` 는 원안 그대로다.

Auth `onCreate` 트리거 함수를 쓰지 않는 이유는 함수가 4개가 되고 배포 단위가 하나 늘기
때문이다. 규칙 세 줄이 같은 보장을 한다.

**앱 작업:** 회원가입 성공 직후 `users/{uid}` 생성. `nickname` 은 가입 폼 값, 카운터 3개는
반드시 `0`. 하나라도 0이 아니면 규칙이 거부한다.

**이 안이 뒤집히면:** 규칙의 `allow create` 가 `if false` 가 되고 트리거 함수를 추가한다.
정반대 방향이라 미리 쓸 수 없다.

## 2. `tickets` 목록 조회는 본인 것만 연다 (E)

```
allow get:  if 본인 티켓이거나 visibility == 'public';
allow list: if 쿼리에 userId == request.auth.uid 가 포함될 것;
```

[screens.md](https://github.com/spencer0124/pindom/blob/main/docs/reference/screens.md) 를
확인한 결과 **남의 티켓을 보여주는 화면이 설계에 없다.** 컬렉션(`/(tabs)/tickets`)은 본인
것이고, 공개 티켓을 목록으로 부르는 지점이 현재 없다.

Firestore 보안 규칙은 결과를 걸러주지 않는다. 목록 조회를 공개 티켓까지 열어두면 앱이
쿼리에 `where('visibility', '==', 'public')` 을 빠뜨렸을 때 **전체가
`permission-denied`** 로 거부되고, 원인이 규칙인지 코드인지 구분하기 어렵다. 소비하는
화면이 없는 동안은 잠가두는 편이 실패 지점을 줄인다.

문서 하나를 직접 읽는 경우(`get`)는 공개 티켓도 허용한다. 나중에 티켓 공유 링크 같은 기능이
생기면 그대로 동작한다.

**앱 작업:** 티켓 목록 쿼리에 항상 `where('userId', '==', 현재 uid)` 를 포함.

**이 안이 뒤집히면:** 남의 공개 티켓을 보여주는 화면이 생길 때 `allow list` 에 조건을 하나
더 여는 것으로 끝난다. 되돌리는 비용이 작아 지금 잠가도 손해가 없다.

## 회신이 필요 없는 항목

아래는 백엔드 단독으로 확정 가능해 회신을 기다리지 않고 Phase 3에서 작성한다.

| 대상 | 규칙 |
| --- | --- |
| `places`, `raffles` | 로그인 사용자 읽기, 쓰기 금지 |
| `tickets`, `raffleEntries` | 클라이언트 쓰기 전면 금지 |
| `verificationSessions` | 읽기·쓰기 전면 금지 |
| `posts` | 본인 글 작성·수정·삭제, 카운트 필드 조작 금지 |
| Storage | 본인 경로만, 이미지 타입만, 용량 상한 |

# Phase 3 결과 — 보안 규칙 작성 후 앱 쪽 확인 사항

`firestore.rules` 와 `storage.rules` 를 작성하면서 계약서·앱 코드와 대조한 결과다. 규칙은 이미
아래 판단대로 쓰여 있고, **이의가 있으면 알려주면 그에 맞춰 고친다.**

## 1. `users` update — 여섯 필드로 정정 (수용)

지적대로 고쳤다. 위 [합의 제안 1번](#1-users-문서는-클라이언트가-만든다-d)의 정정 주석 참고.
`allow create` 는 원안 그대로다.

## 2. 리뷰 — 앱 코드에 맞췄다. 방문 검증은 없다

리뷰 문서 id 를 `ticketId` 로 고정해 "티켓 하나에 리뷰 하나" 를 강제하는 안을 먼저 검토했으나,
**앱 수정을 요구하지 않는 쪽으로 정리했다.** 앱의 `addReview` 는 `addDoc` (자동 id) 을 쓰고
`ticketId` 를 보내지 않는다. 규칙은 그 형태를 그대로 받는다.

대신 **방문 검증이 없다.** 규칙은 컬렉션을 조회할 수 없고 문서 id 로 접근할 수 있는 것만
읽을 수 있어서, 리뷰에 티켓 참조가 없으면 "이 사람이 여기 다녀왔는가" 를 확인할 방법이
존재하지 않는다. 지금 규칙이 대조하는 것은 작성자 신원과 배지뿐이다.

| 열려 있는 것 | 막혀 있는 것 |
| --- | --- |
| 가본 적 없는 장소에 리뷰 작성 | 남의 이름으로 작성 |
| 한 장소에 무제한 작성 | `authorTier` 위조 |
| | `likeCount` 선점·조작 |

**계약서 정정 요청:** write-ownership 의 "one per place" 는 규칙으로 강제되지 않는다.
앱이 리뷰 문서 id 를 `ticketId` 로 쓰고 `ticketId` 를 필드로도 보내기 시작하면, 규칙 두 줄
(`get(tickets/$(ticketId))` 로 소유자·장소 확인)을 더해 방문 검증과 티켓당 1개가 함께 생긴다.
리뷰 화면을 만들 때 판단하면 된다 — 그때까지는 이 상태가 손해가 아니다.

## 3. 타인 `users` 문서 읽기는 닫았다

계약서는 타인의 `nickname`·`avatarUrl`·`tier` 읽기를 허용하지만, **Firestore 규칙은 필드 단위
읽기를 막을 수 없다.** 문서를 열면 `email` 까지 함께 나간다.

`screens.md` 에 타인 프로필 화면이 없고, 피드·리뷰는 작성자 정보를 자기 문서에 비정규화해
들고 있어(`authorNickname`, `authorAvatarUrl`, `authorTier`) 실제로 타인 문서를 읽는 지점이
없다. 앱 코드에서도 `users` 를 읽는 곳은 본인 문서뿐이다.

화면이 생기면 그때 둘 중 하나를 고르면 된다 — 공개 3필드만 `userProfiles/{uid}` 로 분리하거나,
`email` 노출을 감수하고 문서 전체를 열거나.

**계약서 변경 요청:** write-ownership 의 `users` 읽기 열을 "own document" 로.

## 4. 게시글도 닉네임·등급을 대조한다

`posts.create` 가 `authorNickname` 과 `authorTier` 를 클라이언트에서 써 보내므로, 규칙이
`users` 문서와 대조한다. 대조가 없으면 남의 닉네임과 `clubGo` 배지를 달고 글을 쓸 수 있다.
리뷰도 같다. 쓰기 1건당 문서 읽기 1건이 붙지만 위조를 막는 값으로는 싸다.

**앱 영향 없음** — 지금 코드가 이미 본인 `users` 문서에서 읽어 넣고 있다.

**계약서 변경 요청 2건:** `posts` 스키마에 앱이 실제로 쓰고 있는 `boardId` 와 `authorTier` 가
빠져 있다. write-ownership 의 "never `authorTier`" 는 이 대조로 대체된다.

## 5. Storage 목록 조회를 닫았다

Storage 에서 `read` 는 `get` 과 `list` 를 함께 뜻한다. 열어두면 누구나
`tickets/{남의 uid}/` 를 훑어 **비공개 티켓 사진까지** 꺼낼 수 있다. 앱은 문서에 저장된 URL 로
접근하므로 목록이 필요 없다 — `get` 만 열고 `list` 는 닫았다. 업로드는 본인 경로·이미지 타입·
10MB 상한.

## 6. 복합 인덱스 2개

앱의 실제 쿼리에 필요해 `firestore.indexes.json` 에 넣었다.

| 컬렉션 | 필드 | 쓰는 곳 |
| --- | --- | --- |
| `tickets` | `userId` · `visibility` · `issuedAt` desc | 컬렉션 / 보관함 |
| `posts` | `boardId` · `createdAt` desc | 커뮤니티 피드 |

## 7. 규칙 재검토에서 고친 것 — 결함 5건

작성한 규칙을 앱 코드와 다시 대조해 다섯 건을 고쳤다. 앞의 두 건은 그대로 배포했으면 문제가
됐을 것이다.

| 결함 | 증상 | 조치 |
| --- | --- | --- |
| 신규 가입자의 `tier` 부재 | 티켓이 0개인 사용자는 리뷰·게시글을 **쓸 수 없었다**. `tier` 는 `issueTicket` 이 첫 티켓에서 만드는 필드인데, 없는 키를 읽으면 규칙 평가가 예외로 끝난다 | 문서 존재를 먼저 확인하고 `tier` 를 기본값 `club10` 과 함께 읽는다 |
| 가입 시 `tier` 자가 지정 | `allow create` 가 카운터 3개만 고정해, 가입 요청에 `tier: 'clubGo'` 를 끼워 넣으면 이후 배지 대조가 **위조된 값 기준으로 통과**했다 | 가입 페이로드에 `tier` 가 있으면 거부. 앱은 보내지 않으므로 영향 없음 |
| `createdAt` 위조 | 피드가 `createdAt` 내림차순이라 미래 시각을 넣으면 맨 위를 영구 점유 | 서버 시각(`request.time`)과 대조. 앱은 `serverTimestamp()` 를 써 그대로 통과 |
| `visibility` 값 미검사 | `'x'` 가 저장되면 컬렉션에도 보관함에도 안 잡혀 티켓이 사라짐 | `'public'` / `'private'` 만 허용 |
| Storage 삭제 불가 | 삭제 요청에는 `request.resource` 가 없어 이미지 검사 함수가 예외로 끝났다. 글을 지워도 파일이 남음 | `create/update` 와 `delete` 를 분리 |

`tier` 기본값이 `club10` 인 것은 앱의 읽기 기본값(`oneOf(d.tier, TIERS, 'club10')`)과 위 6번의
0–19 구간에 모두 맞는다.

## 8. `places.reviewCount` 는 값을 쓸 주체가 없다

계약서에 **Function-only** 로 표기돼 있으나, 리뷰는 클라이언트가 직접 쓰고 함수는 셋으로 고정했으며
그중 리뷰를 건드리는 것이 없다. 이 필드는 영원히 `0` 이다.

앱은 리뷰 목록을 통째로 읽으므로 화면에서 배열 길이를 쓰면 된다. **계약서에서 이 필드를 빼자고
요청한다.** 카운터 하나를 위해 네 번째 함수를 만들 이유가 되지 못한다.

## 9. Tier 임계값 — 회신을 기다리지 않고 정한다

`issueTicket` 이 트랜잭션 안에서 `tier` 를 다시 계산하므로 이 값 없이는 함수를 끝낼 수 없었다.
회신을 더 기다리는 대신 프로토타입에 맞춰 아래로 정하고 Phase 4 를 진행한다.

프로토타입 카드에 `TICKETS OWNED 12` 와 `TIER 10—19` 가 나란히 찍혀 있다. 12장이 10—19 구간에
들어가므로 구간 폭은 10이다.

| tier | `ticketsIssued` |
| --- | --- |
| `club10` | 0 – 19 |
| `club20` | 20 – 29 |
| `clubGo` | 30 이상 |

- **전역이다.** 계약서의 `tier` 는 `users.ticketsIssued` 에서 파생되고 그 카운터가 전역이다.
  아티스트별로 하려면 사용자 문서에 아티스트별 카운터가 필요해 스키마가 커진다.
- **발행 수 기준이지 잔액 기준이 아니다.** 프로토타입은 `TICKETS OWNED` 옆에 배지를 뒀지만,
  잔액으로 계산하면 응모로 티켓을 쓸 때마다 등급이 내려간다. 등급은 내려가지 않아야 한다.
- `clubGo` 의 30은 구간 폭을 그대로 이어붙인 값이다. 근거가 프로토타입에 없다.

`issueTicket` 안의 상수 하나이므로 **바꾸는 비용은 함수 재배포 한 번**이다. 다른 값이면
알려주면 그날 바꾼다. 스키마도 규칙도 건드리지 않는다.

## 남은 것

앱 쪽 회신이 없어도 Phase 4 를 진행할 수 있다. 위 판단 중 이견이 있는 항목만 알려주면 된다.
