## 1. Phase 3 — 보안 규칙 (`1b8d080`)

전면 차단 상태(`allow read, write: if false`)에서 실제 규칙으로 바꿨다. 기준은 계약서의
write-ownership 표.

### 앱 쪽 지적을 받아 고친 것

리뷰 당시 제안한 `users` update 규칙이 `nickname`·`avatarUrl` 두 필드만 허용했다. 계약서는
여섯 필드를 허용한다. 두 개로 배포했으면 **프로필 편집·언어·최애 찾기가 전부
`permission-denied`** 로 죽었다. 여섯 필드로 정정했다. `allow create` 는 원안 그대로다.

### 규칙을 쓰면서 내린 판단 넷

| 판단 | 이유 |
| --- | --- |
| 타인 `users` 문서 읽기를 닫았다 | Firestore 는 필드 단위 읽기를 막을 수 없다. 문서를 열면 `email` 까지 나간다. 타인 프로필 화면이 설계에 없고 피드·리뷰는 작성자 정보를 이미 비정규화해 들고 있어, 읽을 지점이 실제로 없다 |
| 게시글·리뷰의 `authorNickname`·`authorTier` 를 `users` 문서와 대조한다 | 앱이 두 값을 클라이언트에서 써 보낸다. 대조가 없으면 남의 닉네임과 `clubGo` 배지를 달고 글을 쓸 수 있다 |
| Storage 목록 조회(`list`)를 닫았다 | Storage 에서 `read` 는 `get` 과 `list` 를 함께 뜻한다. 열어두면 누구나 `tickets/{남의 uid}/` 를 훑어 **비공개 티켓 사진**을 꺼낼 수 있었다 |
| 복합 인덱스 2개를 정의했다 | 앱 코드에 이미 있는 쿼리다 — 컬렉션·보관함, 커뮤니티 피드 |

### 리뷰 규칙은 앱 코드에 맞췄다 (`5cf0402`)

리뷰 문서 id 를 `ticketId` 로 고정해 "티켓 하나에 리뷰 하나" 를 강제하는 안을 먼저 만들었으나,
앱 수정을 요구하지 않는 쪽으로 되돌렸다. 앱의 `addReview` 는 `addDoc`(자동 id)을 쓰고
`ticketId` 를 보내지 않는다.

**대가는 방문 검증이다.** 규칙은 컬렉션을 조회할 수 없고 문서 id 로 접근 가능한 것만 읽으므로,
리뷰에 티켓 참조가 없으면 "이 사람이 여기 다녀왔는가" 를 확인할 방법이 존재하지 않는다. 되살리는
경로는 `firestore.rules` 에 `ponytail:` 주석으로 남겼다.

같은 커밋에서 tier 임계값도 확정했다 — 프로토타입의 `TICKETS OWNED 12` / `TIER 10—19` 에서
구간 폭 10을 읽었다. `club10` 0–19, `club20` 20–29, `clubGo` 30+, **발행 수 기준·전역**.
잔액 기준이면 응모할 때마다 등급이 내려간다.

### 자체 검토로 찾은 결함 5건 (`8d65d02`)

테스트 15건이 통과하고 있었지만 **시드 데이터가 현실보다 관대했다.** 앱의 `signUp` 은 `tier` 를
쓰지 않는데 테스트는 넣고 시작했다. 시드를 실제 페이로드와 같게 맞추자 옛 규칙에서 7건이 실패했다.

| 결함 | 실제로 무엇이 됐나 |
| --- | --- |
| 신규 가입자의 `tier` 부재 | 티켓이 0개인 사용자는 리뷰도 글도 **쓸 수 없었다.** 없는 키를 읽으면 규칙 평가가 예외로 끝난다. 문서 존재를 먼저 확인하고 기본값 `club10` 과 함께 읽는다 |
| 가입 시 `tier` 자가 지정 | `allow create` 가 카운터 3개만 고정해, `tier: 'clubGo'` 를 끼워 넣으면 저장됐다. 그 뒤 배지 대조가 **위조된 값을 기준으로** 통과한다 |
| `createdAt` 위조 | 피드가 `createdAt` 내림차순이라 미래 시각 하나로 맨 위를 영구 점유할 수 있었다. 서버 시각과 대조한다 |
| `visibility` 값 미검사 | `'x'` 가 저장되면 컬렉션에도 보관함에도 안 잡혀 티켓이 사라진다 |
| Storage 삭제 불가 | 삭제 요청에는 `request.resource` 가 없어 이미지 검사 함수가 예외로 끝났다. 글을 지워도 파일이 남았다 |

## 2. Phase 4 — Cloud Functions (`aa8e17d`)

`functions/src/logic.ts` (순수 계산) 와 `functions/src/index.ts` (콜러블 셋) 두 파일이다. 판정
산수를 Firebase 에서 떼어낸 이유는 하나다 — 거리와 속도는 값 하나로 티켓이 나오고 안 나오고가
갈리는 자리라 에뮬레이터 없이 `node --test` 로 경계를 찍을 수 있어야 한다.

임계값은 전부 `logic.ts` 상단에 모았다. GPS 는 기기마다 다르게 흔들려 실측을 보고 조정하게 된다.

### 구현하며 내린 판단

- **`verifyLocation` 은 거부를 throw 하지 않는다.** 66m 떨어져 있는 것은 정상적인 결과이고,
  인증 실패 화면이 거리·반경·정확도를 표로 렌더링한다
- **정확도로 거부된 측정은 세션에 기록하지 않는다.** 오차 200m 짜리 샘플이 배열에 들어가면 다음
  속도 계산을 오염시킨다
- **기준 좌표는 언제나 `places` 문서에서 읽는다.** 클라이언트가 보낸 좌표는 판정 대상이다
- **`issueTicket` 의 쿨다운 쿼리 하나가 두 가지를 답한다** — 30일 안인지, 그리고 결과가 비어
  있으면 첫 방문이라 `placesVisited` 를 올릴지
- **`photoPath` 는 `tickets/{uid}/` 접두사와 객체 존재를 둘 다 본다.** 접두사를 안 보면 남의
  사진 경로를 붙여 티켓을 만들 수 있다
- **`enterRaffle` 은 문서 id 자체가 멱등 장치다.** `{uid}_{raffleId}_{key}` 에 문서가 이미 있으면
  차감 없이 기존 id 를 돌려준다. 별도 멱등 컬렉션도 조회도 없다

### 계약서에 값이 없어 정한 것

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 그랜트 유효시간 | 10분 | 앱 목 구현 `mock.ts` 가 쓰던 값 |
| 응모 차감 순서 | 오래된 티켓부터 | 규정 없음. 사용자에게 유리하고 설명하기 쉽다 |

### 테스트를 짜다 함수가 옳다고 확인된 것 둘

- 두 번째 장소를 13km 떨어뜨렸더니 인증이 실패했다 → **직전 티켓 대비 속도 검사가 제대로 걸린
  것**이다. 테스트 좌표를 150m 로 옮겼다
- 사진 경로 검사 테스트가 `cooldown_active` 를 돌려줬다 → **쿨다운이 먼저 걸리는 순서가 맞다**

## 3. Phase 5 — 배포와 시드 (`8191382`, `845c707`)

시드는 앱 레포 `src/mocks` 에서 옮겼다. 문자열은 `{ ko, en }` 맵으로 바꿨고 **카운터는 전부 0**
이다 — 목의 `ticketCount: 1284` 같은 숫자는 화면에서만 그럴듯하고 첫 발행에서 어긋난다.

배포하며 세 번 막혔고 원인이 전부 문서에 없던 것이라 README 「배포 상태」에 남겼다.

| 증상 | 원인 |
| --- | --- |
| `iam.serviceaccounts.actAs denied ...-compute@developer` | 2세대 함수는 Cloud Run 위에서 돌고 실행 주체가 Compute Engine 기본 서비스 계정이다. `compute.googleapis.com` 을 켜야 그 계정이 생긴다 |
| `functions:artifacts:setpolicy` 가 저장소를 못 찾음 | 기본 리전이 `us-central1` 이다. `--location asia-northeast3` |
| 시드에서 `Could not load the default credentials` | `firebase login` 은 CLI 토큰이라 Admin SDK 가 쓰지 못한다. `gcloud auth application-default login` 이 필요하다 |

**서비스 계정 키는 쓰지 않았다.** 이 저장소는 public 이고 키 파일 하나면 그 전제가 무너진다.

## 4. 배포 후 검토 (`5ebac0f`, `7a21909`, `7fb13df`)

배포가 끝난 상태에서 다시 훑어 세 건을 고쳤다. 둘은 실 운영에서만 드러났을 것이다.

| 결함 | 무엇이 됐나 |
| --- | --- |
| 그랜트 검사가 트랜잭션 밖에만 있었다 | 같은 그랜트로 동시에 두 번 호출하면 둘 다 통과해 **티켓이 두 장** 나온다. 인증 한 번에 티켓 한 장이라는 성질이 무너지고, 티켓은 응모로 실제 값어치가 붙는 물건이다. 검사를 트랜잭션 안에서 한 번 더 한다 |
| 시드 재실행이 카운터를 0으로 되돌렸다 | 이미 적재가 끝난 뒤였다. 한 번 더 돌렸으면 `ticketCount` 가 0이 되고, 다음 발행 전까지 드러나지 않는다. 이미 있는 문서에는 내용만 병합한다 |
| `capturedAt` 위조 | 시각이 클라이언트 값이면서 속도 계산의 분모다. 과거 시각을 넣으면 어떤 이동도 느려 보여 속도 검사가 통째로 무력해진다. 서버 시각 ±5분 |

이어서 구조 검토를 하고 셋을 손봤다.

| 변경 | 효과 |
| --- | --- |
| 직전 티켓 대비 속도 검사를 세션 첫 측정에서만 | 인증 핑당 문서 읽기 **4 → 2**. 판정 강도는 그대로 — 도착 자체는 계속 판정하고, 이후 측정은 세션 내부 검사가 덮는다 |
| `verificationSessions.readings` 와 `posts.imageUrls` 색인 해제 | 쿼리에 한 번도 쓰지 않는 배열 필드다. Firestore 는 배열 원소마다 색인해 쓰기 비용만 늘었다 |
| `maxInstances: 10` | App Check 이 초기 릴리스에서 빠져 있고 함수 URL 은 공개다. 스크립트로 때리면 인스턴스가 무한히 늘고 그대로 청구서가 된다 |

마지막으로 인덱스 배포가 남기던 경고의 정체를 확인했다. **파일에 없는 field override 가 세션
TTL 정책이었다** — 언젠가 `--force` 를 붙이는 순간 세션 정리가 조용히 꺼진다. 만료된 세션이
쌓이는데 그 사실은 아무 데서도 드러나지 않는다. `firestore.indexes.json` 에 `"ttl": true` 로
선언해 파일이 실제 상태를 담게 했다.

## 6. 검증 방법

테스트는 세 겹이다. 규칙을 고치면 첫째와 둘째가, 함수를 고치면 셋째가 답한다.

```bash
node --test functions/test/logic.test.mjs                       # 판정 산수 14건, 에뮬레이터 불필요
firebase emulators:exec --only firestore,storage \
  "node --test --test-force-exit functions/test/rules.test.mjs"  # 보안 규칙 18건
firebase emulators:exec --only auth,firestore,storage,functions \
  "node --test --test-force-exit functions/test/functions.test.mjs"  # 함수 동작 13건
```

에뮬레이터는 Java 를 쓴다. 없으면 `brew install openjdk` 후 PATH 에 추가한다.

함수 테스트는 회원가입 → GPS 인증 → 사진 업로드 → 티켓 발행 → 응모까지 실제로 태우고,
트랜잭션이 문서에 남긴 결과(잔액·카운터·`spent`·갤러리)까지 확인한다.

> **테스트를 고칠 때의 함정** — 위 결함 8건 중 둘은 시드 데이터가 현실보다 관대해서 가려져
> 있었다. 테스트가 실패하면 규칙·함수를 의심하기 전에 **시드가 앱의 실제 페이로드와 같은지**
> 먼저 보라. 새 검사를 넣었으면 옛 규칙에서 그 케이스가 실제로 실패하는지도 확인하라 —
> 통과만 하는 테스트는 아무것도 증명하지 않는다.

## 8. 남은 것

백엔드가 대기 중인 작업은 없다. 아래는 앱이 붙은 뒤 판단할 것들이다.

- **등급 경계** — `clubGo` 의 30은 프로토타입에 근거가 없다. 다른 값이면 상수 하나와 재배포
- **리뷰 방문 검증** — 앱이 리뷰 문서 id 를 `ticketId` 로 쓰고 필드로도 보내면 규칙 두 줄로
  되살아나고, 티켓당 1개까지 함께 생긴다
- 결제 예산 알림 (콘솔), `firebase-functions` 6 → 7, 출시 직전 `verifyLocation` 상시 인스턴스
- Firestore 백업/PITR — 출시 후 필수
